# Мониторинг PostgreSQL по слоям: как пользоваться

```bash
docker compose up -d          # полный сброс данных: docker compose up -d -V --build
```

| Ссылка | Что это | Когда открывать | refresh |
|---|---|---|---|
| http://localhost:3002/d/pg-overview | **Обзор** — светофоры с порогами | всегда начинать отсюда | 15s |
| http://localhost:3002/d/pg-layered | **Слои** — инцидент и его причина (ОС → инстанс → объекты → workload → репликация) | идёт инцидент | 1m |
| http://localhost:3002/d/pg-queries | **Запросы** — форензика: топы по времени/CPU/диску/WAL/temp, разброс латентности, тексты запросов | оптимизация и разбор «кто виноват» | 1m |
| http://localhost:3002/d/pg-hygiene | **Долг и конфигурация** — bloat, индексы, sequence, размеры, настройки инстанса и ядра | по расписанию, не в инцидент | 5m |
| http://localhost:3002/d/pg-monitoring | **Здоровье мониторинга** — up, длительность scrape, лимиты, кардинальность | раз в неделю и когда метрики врут | 5m |

Дашборды разделены по назначению намеренно: инцидентный триаж, форензика
запросов, накопленный долг и самопроверка мониторинга — разные задачи, разный
ритм и разная цена. Один общий дашборд на 91 панель делал ~600 запросов в минуту
на каждого открывшего и заставлял искать симптом среди справочников.

Инцидентный дашборд устроен так, чтобы всё нужное было видно без раскрытия:
секции **Instance: Throughput & IO** и **Instance: Health** разделяют «сколько
работы делает сервер» и «здоров ли он», а глубокая атрибуция IO
(**Instance: IO Attribution**) свёрнута — свёрнутые панели не выполняют запросов
и разворачиваются, только когда дошли до вопроса «кто именно ест диск».

## Идея

Проблема проявляется на одном слое, а причина живёт на другом: тормозит запрос
(workload), потому что чекпоинт залил диск (инстанс), потому что WAL-шторм
переполнил `max_wal_size` (workload же и виноват). Дашборды построены, чтобы это
разматывать сверху вниз:

1. **Обзор** отвечает «что плохо» — один экран светофоров с порогами.
2. Иконка-ссылка у заголовка панели проваливает в нужную секцию дашборда
   «Слои» — с тем же временным диапазоном и той же нодой.
3. В «Слоях» ищете «почему», двигаясь между секциями; когда виновником
   оказывается запрос — ссылка **Show query text** на любой top-панели уводит
   в «Запросы» с уже подставленным queryid.

Аннотации на всех дашбордах отмечают события, которые ломают чтение графиков:
promote/failover (рост timeline), рестарт PostgreSQL и сброс pg_stat_statements
(иначе обнуление счётчиков читается как «нагрузка исчезла»). Деплои и DDL
мониторинг не видит — их присылает CI прямо в Grafana:

```bash
curl -XPOST http://grafana/api/annotations -H 'Content-Type: application/json' \
  -d '{"dashboardUID":"pg-layered","time":'"$(date +%s000)"',"tags":["deploy"],"text":"release 1.42"}'
```

Переключатели сверху: **Нода** (pg01/pg02 — идентичность, не роль; текущую роль
показывает панель Node Roles), **Хост** и — в «Слоях» — **База** для панелей
объектного слоя. Подробнее в разделе «Модель идентичности и failover».

## Модель идентичности и failover

Правило одно: **лейблы описывают, ГДЕ снято, метрики — ЧТО происходит.**
Роль (primary/standby) — это состояние, поэтому её нет ни в одном лейбле:
иначе переключение ролей переименовало бы серии и разорвало историю.

| Лейбл | Что это | Откуда |
|---|---|---|
| `cluster`, `env` | логический кластер и контур | `external_labels` в prometheus.yml |
| `node` | **идентичность ноды** (pg01/pg02), не роль | `labels:` в sql_exporter.yml |
| `host` | ОС-хост — джойн с node_exporter | labels скрейпа в prometheus.yml |
| `datname` | база (только per-database метрики) | `current_database()` в коллекторах |

Роль и идентичность кластера отдают метрики: `pg_in_recovery` (0 = primary,
1 = standby), `pg_role_info{role=...}`, `pg_cluster_info{system_identifier,
cluster_name}`, `pg_timeline_id`. `system_identifier` одинаков у всех нод одного
кластера — это доказательство членства (и детектор «DSN уехал на чужой кластер»).

Панели, которым нужна конкретная роль, выбирают её в PromQL, а не в конфиге:

```promql
pg_sync_standbys and on(node) (pg_in_recovery == 0)   # то, что есть только на primary
pg_standby_wal_receiver_up and on(node) (pg_in_recovery == 1)   # только на standby
```

**Что происходит при failover:** ничего не переконфигурируется. Ноды сохраняют
свои `node`-лейблы, линия в панели **Node Roles** переезжает между 0 и 1,
`pg_timeline_id` инкрементится (и рисует красную аннотацию «Promote / failover»
на всех панелях), метрики репликации сами появляются на новой паре. Набор
коллекторов у всех нод одинаковый — включая `pg_standby`, чтобы у новой реплики
метрики были сразу, а не после правки конфига.

Что проверить сразу после переключения: в **Node Roles** ровно одна линия на 0
(две = split brain, ни одной = писать некуда), в **Timeline ID** обе ноды на
одном таймлайне (разные = standby не пошёл за новым primary, нужен pg_rewind).

## Слои: на что смотреть и какие выводы делать

Попанельная шпаргалка слоя ОС (что допустимо / как чинить) — в [PANELS.md](PANELS.md).

### 1. ОС — «виновато ли не-Postgres и во что упёрлось железо?»

- **steal** (линия в «CPU по режимам») стабильно > 2–5% — гипервизор отдаёт
  ваш CPU соседям; **PSI (pressure)** — процессы уже стоят в очереди за
  CPU/диск/память. Если плохо здесь — ниже можно не копать: чинится
  инфраструктура, не база.
- **Железо и параметры ядра** (таблица + чеклист внизу слоя) — ядра / RAM /
  swap (против них читаются load, «Память: доступно, %» и AAS в слое 4) и
  swappiness / overcommit / dirty / hugepages против рекомендаций; чего
  node_exporter не отдаёт (THP, I/O scheduler, governor, лимиты юнита) —
  в чеклисте рядом.
- **CPU и load** против числа ядер: load выше ядер = очередь на исполнение.
- **Диск: латентность** растёт при прежних IOPS → диск деградировал или сосед
  по хранилищу; растёт вместе с IOPS → это ваша же нагрузка (ищите её в слое 2).
- **Диск: свободно, %** — смотреть тренд: WAL, temp-спиллы и логи съедают
  место за минуты, а не за дни.
- **Сеть rx/tx** — потолок NIC, всплески репликации/бэкапов.

В проде добавьте hardware-видимость: bare metal — SMART (smartctl_exporter),
ECC, RAID/IPMI; облако/VM — метрики провайдера (burst-кредиты диска,
троттлинг IOPS). В демо доступны только steal и PSI.

### 2. Инстанс PostgreSQL — «здоров ли сам сервер?»

- **Сессии по состояниям**: рост `idle` — приложение без пулера; рост
  `idle in transaction` — источник блокировок и распухания (см. слой 4).
- **Чекпоинты timed vs requested** — главная панель слоя. Появились
  `requested` → WAL растёт быстрее `max_wal_size`, чекпоинты приходят кучно;
  их волну видно ниже.
- **pg_stat_io (кто ПИШЕТ / кто ЧИТАЕТ / fsyncs)** — атрибуция диска по
  подсистемам: checkpointer, bgwriter, autovacuum или клиентские бэкенды.
  Ответ на вопрос «куда уходят IOPS» — здесь.
- **Cache hit ratio** — тревожен не уровень, а устойчивое падение тренда:
  рабочее множество перестало влезать в память. Проценты обманчивы — сверяйте
  с абсолютной панелью чтений pg_stat_io.
- **WAL байт/с + wal_buffers_full** — кто-то начал массово писать;
  `wal_buffers_full` растёт → WAL-буферов не хватает.
- **Локи по режимам** — фон; очередь ожидающих смотреть в слое 4.
- **Ключевые настройки** (живая таблица внизу слоя) — пороги, к которым
  апеллируют панели: max_wal_size ↔ чекпоинты, work_mem ↔ temp-спиллы,
  shared_buffers ↔ cache hit; «ЖДЁТ РЕСТАРТА» = изменено, но не применено.

### 3. Базы и объекты — «не копится ли долг в данных?»

- **XID/MXID age** — дистанция до wraparound; рост без плато = autovacuum
  не успевает замораживать. Это единственная метрика, которая может остановить
  базу целиком.
- **Dead tuples / таблицы, ждущие vacuum** — если растёт при живом autovacuum,
  его кто-то держит (см. xmin в слое 4) или ему мало воркеров.
- **Размеры таблиц** — резкий излом = bloat после массовых UPDATE/DELETE.
- **Unused / invalid индексы, заполненность sequence** — тихий долг: лишняя
  запись на каждом UPDATE и переполнение счётчиков.

### 4. Workload — «что делает нагрузка и кто именно виноват?»

- **Commit/rollback** (панель «Транзакции/с» — в слое 2) — пульс: провал
  commit при росте ожиданий = встали в очередь; рост rollback =
  ошибки/deadlocks/ретраи.
- **Средняя латентность и перцентили по queryid**: разрыв p99/p50 по времени —
  горстка тяжёлых запросов на фоне быстрой массы; концентрацию трафика смотреть
  по top-10 частоты вызовов на фоне общего QPS.
- **DB Load по классам ожиданий (AAS)** — куда уходит время базы: CPU, IO,
  Lock, WAL. Плато класса Lock высотой N = N сессий стоят в очереди за
  блокировкой. AAS, приближающийся к числу ядер, — насыщение.
- **Top-10 по времени / вызовам / WAL / temp / чтению с диска** + панель
  «Top запросов по ожиданиям» — виновник по любой оси; текст запроса — в
  таблице «Расшифровка queryid».
- **Старейшая транзакция / idle-in-xact / xmin-горизонт** — долгие транзакции
  держат vacuum: жертвы будут в слое 3, причина — здесь.
- **Планы медленных запросов** — auto_explain пишет их в лог
  (`docker logs example-postgres-1`): queryid из плейн-флип детектора ищется
  по `qid=<queryid>` в префиксе строки или по Query Identifier внутри плана.

### 5. Репликация — «жива ли пара?»

- **Лаг в байтах** (не догоняет по сети/диску) vs **в секундах** (насколько
  устарели чтения со standby).
- **Синхронных реплик** — при sync-репликации смерть standby останавливает
  коммиты на primary: это первое, что смотреть при «всё зависло».
- **Слоты: удержание WAL** — мёртвый потребитель слота копит WAL до
  переполнения диска primary.

## Типовые маршруты

- **«Всё медленно»** → обзор → AAS: класс Lock → долгие транзакции и top по
  ожиданиям; класс IO → pg_stat_io «кто читает/пишет» → top по чтению/WAL;
  всё в CPU → top по времени и частоте.
- **«Диск нагружен»** → pg_stat_io: checkpointer → чекпоинты requested? →
  панель WAL → top-10 по WAL → queryid → текст запроса.
- **«Коммиты встали»** → синхронных реплик = 0? → лаг/walreceiver на standby.
- **«Место кончается»** → размер pg_wal (слот? архиватор в ошибках?) →
  temp-файлы (спиллы) → размеры таблиц (bloat).

## Потренироваться

`docker compose run --rm --no-deps --entrypoint sh load /load/chaos.sh` —
~11 минут управляемых аварий (блокировки → deadlocks → temp-спиллы →
WAL-шторм → пиннинг xmin).
Каждая фаза запускается и отдельно — команда в шапке `load/chaos/*.sql`.

Карта метрик и слепых зон — комментарии в `sql_exporter/collectors/*.yml`
и заметки аудитов `../fixes.txt`, `../rollback_cumulative_stats.txt`.
